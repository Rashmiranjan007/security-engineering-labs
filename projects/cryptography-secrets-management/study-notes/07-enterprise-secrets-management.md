# Module 7 — Enterprise Secrets Management for Cloud, Kubernetes and CI/CD

## 1. Secrets and their risk

Secrets include passwords, API keys, OAuth client secrets, database credentials, cloud access keys, private keys, certificates, signing tokens, webhook secrets, and service credentials. A secret is valuable because it grants an identity or capability. Its risk depends on permissions, lifetime, exposure, and reachable resources.

A central secret store does not automatically solve identity or authorization. The application retrieving the secret must itself be authenticated and authorised.

## 2. Secrets management lifecycle

- Discover and inventory secrets, owners, consumers, permissions, and environments.
- Classify secrets by privilege, data sensitivity, and blast radius.
- Generate high-entropy credentials and avoid shared accounts.
- Store in a managed secret platform with strict access policy.
- Deliver just in time or at runtime; avoid source code and build artifacts.
- Rotate automatically where possible and validate consumer reload.
- Revoke immediately on compromise or ownership change.
- Audit retrieval, modification, access failures, and anomalous usage.
- Remove unused credentials and confirm downstream copies are addressed.

## 3. Static versus dynamic credentials

Static credentials remain valid until rotated or revoked. They are easy to integrate but create exposure windows and lifecycle burden.

Dynamic credentials are issued for a limited time or session and can be scoped to a workload or request. Examples include short-lived cloud role credentials and database credentials generated by a secrets platform. Dynamic credentials reduce long-term exposure but require reliable identity, renewal, revocation, and outage handling.

## 4. Workload identity and federation

Prefer workload identity to embedding cloud access keys. A workload presents an identity assertion to a trusted identity provider; the cloud service validates issuer, audience, subject, and trust conditions and issues short-lived credentials.

For EKS, understand IAM Roles for Service Accounts (IRSA) and EKS Pod Identity. Scope role trust to the intended cluster/workload identity and permissions to required APIs. Prevent arbitrary pods from using privileged service accounts. Protect node roles and metadata access.

For CI/CD, OpenID Connect federation can exchange a job identity token for short-lived cloud credentials. Restrict repository, branch, environment, audience, and workflow identity claims. Avoid long-lived cloud keys in CI variables.

## 5. Kubernetes Secrets

Kubernetes Secret objects store data encoded as base64 in API representations; base64 is not encryption. Security depends on encryption at rest for etcd, API server access, RBAC, namespace boundaries, node and backup protection, and workload access controls.

Important controls:
- Enable encryption at rest and protect encryption configuration and keys.
- Restrict get/list/watch permissions for Secrets.
- Avoid broad service accounts and default service account token automount where not needed.
- Mount only required secrets into only the intended containers.
- Use external secret stores or CSI integrations when they fit the threat model.
- Do not commit populated Secret YAML files.
- Protect etcd snapshots and cluster backups.
- Audit Secret reads and watch for unexpected access.

Environment variables can leak through diagnostics, process inspection, crash reports, or accidental logging. File mounts are not inherently safe either; process and filesystem access still need protection.

## 6. AWS secret storage patterns

AWS Secrets Manager supports secret lifecycle, versioning, rotation integrations, and access through IAM. Systems Manager Parameter Store offers parameter storage with different feature and cost characteristics. AWS KMS can protect supported secret values and data keys.

Design decisions include:
- Secret versus configuration parameter.
- Required rotation and version staging.
- Cross-account access model.
- KMS key and resource policy.
- Network path and endpoint access.
- Caching and stale credential handling.
- Audit and alerting.
- Recovery and regional availability.

## 7. CI/CD and developer workflows

- Use OIDC federation and short-lived tokens.
- Scope permissions to a single job and environment.
- Mask secrets but do not rely on masking as a security boundary.
- Disable shell tracing and avoid verbose dumps near secrets.
- Prevent untrusted pull requests from accessing deployment credentials.
- Protect production environments with approvals and branch restrictions.
- Scan repositories, commits, build artifacts, container images, and logs.
- Treat Terraform state and plan files as sensitive.
- Rotate immediately when exposure is suspected; deleting a line from the latest commit does not remove it from Git history, forks, caches, or logs.

## 8. AI application secrets

AI services often use provider API keys, vector database credentials, object storage credentials, signing keys, and tool integration tokens. Keep them out of prompts, retrieved documents, model context, frontend bundles, notebooks, traces, and training data. Model-generated text is untrusted and must never be treated as a secret-store authorization decision.

Use separate credentials for each service and environment, enforce budget and capability scopes, redact observability data, and monitor unexpected provider calls or secret retrieval.
